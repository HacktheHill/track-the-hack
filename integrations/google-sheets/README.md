# Google Sheets integration

[`Code.gs`](./Code.gs) and [`Sidebar.html`](./Sidebar.html) belong in the bound Apps Script project for the restricted Tally response Sheet. **Track the Hack → Pass activation** opens the day-of sidebar, whose single action is **Show pass activation QR**. The separate pre-event **Track the Hack → Prepare accepted RSVP invitations** command prepares every response currently marked Accepted; it does not depend on the selected row.

Select any cell in one response row whose **Admission status** is **Accepted**, then press the button. It saves or reuses a stable participant ID and opens a one-time, five-minute QR that the participant scans to activate their pass. The claim API also creates or updates the minimal participant record if needed. The day-of button does **not** send an RSVP invitation, confirm an RSVP, or change the Sheet's RSVP status. Repeated clicks reuse the display window, which the organizer can move and maximize on another screen. Browsers may block popup creation or automatic fullscreen; in that case the sidebar shows an **Open QR** link. A failed request can be retried with the same ID.

Only the participant ID, T-shirt size, coarse meal category, acceptance expiry, and walk-in flag go to Tracker. Names, email addresses, Tally IDs, waivers, and detailed dietary answers remain in the Sheet. The response-row columns hold RSVP data from the separate pre-event process, as well as the day-of QR expiry and last sync time. This workflow does not require a new **Track Operations** tab.

## Provisioning before RSVP invitations

Provisioning means assigning a stable opaque participant ID in the Sheet and creating or updating the minimal Tracker record for that ID. Tracker creates a separate, stable, signed RSVP-management link; the participant ID alone can no longer change an RSVP. The one-click **Prepare accepted RSVP invitations** menu command checks and processes every row whose recorded **Admission status** is `Accepted`, `Accepté`, or `Acceptée`. It provisions that status-defined audience in bounded API batches, reports the completed count, and does not depend on the selected range, filters, or hidden rows. A validation error stops the operation before provisioning; a failed or incomplete API batch must be retried before exporting invitation recipients. The command is deliberately separate from the day-of sidebar, and an automatic edit trigger is not installed.

For a controlled E2E test, set the non-secret `TRACK_TEST_SUBMISSION_ID` script property to one approved test submission and run `prepareTestSubmissionForRsvp()` instead. It touches only that Accepted submission. Remove the property after testing. Re-running preparation reuses Sheet-owned participant IDs and preserves existing signed links on failed requests; a successful reconciliation updates **RSVP Status** and **RSVP Refreshed At**. The old selection-based acceptance and RSVP-preparation entrypoints are blocked. Do not use the old **Track Operations** tab for new participants.

Existing operational IDs are still read from **Track Operations** when a response row first receives an ID, avoiding a second identity for the same submission. Do not delete the old tab until every prior participant ID has been reconciled into the response rows. A lead-approved walk-in uses its existing response row: set **Admission status** to Accepted and **Walk-In** to true, then issue a pass from the sidebar. It does not need a late RSVP.

## Dietary repair for existing participants

The mapper marks allergies, intolerances, free-text requirements, and combinations of simple categories as **OTHER**, so the food scanner asks staff to contact the food lead. Confirm the multiple-simple-category policy with that lead before a campaign. After the response-column migration, `reviewExistingDietaryCategories()` identifies Accepted rows that already have a participant ID and whose stored category differs from the current answers. `reconcileExistingDietaryCategories()` verifies those IDs exist, then updates **only** the meal category through the dedicated API. It does not issue claims, change RSVP or walk-in state, replace participant sessions, or alter scanner Presence records. Recheck the reported rows and category count after running it; an unknown ID stops its batch without creating a participant.

## Script properties and live update

Set `TRACK_BASE_URL` to the deployed HTTPS Tracker origin, `SHEETS_INTEGRATION_API_KEY` to the matching API secret, and `RSVP_DEADLINE` to the absolute ISO-8601 deadline. If Cloudflare Access protects the API, set **both** `CF_ACCESS_CLIENT_ID` and `CF_ACCESS_CLIENT_SECRET` to the service token already authorized for Tracker. Do not print or paste secret values into logs or issue reports.

To update the live bound script, first back up its existing source and response rows and inspect the existing response headers and **Track Operations** IDs. Replace `Code.gs`, add `Sidebar.html` under that exact filename, save, and reload the Sheet. If the six old Track-owned headers are still the exact final columns, the separate, operator-invoked `migrateLegacyResponseColumnsForRsvp()` preserves their data and expands them to the eleven-column layout. If the ten-column RSVP layout is already installed, use `migrateResponseRsvpRefreshColumn()` instead; it appends only the timestamp header. Both reject other layouts and never run from the menu. Review the [runbook](../../docs/RSVP_EMAIL_RUNBOOK.md) before invoking either. Opening the sidebar makes no Tracker request; pressing **Show pass activation QR** does. This repository change does not update the installed script. Test one known submission first, and verify that its saved ID is unchanged on retry.

## RSVP status

The response-row schema includes **RSVP Status**: `PENDING` (no answer), `CONFIRMED` (attending), or `DECLINED` (not attending). A successful preparation reconciles the state and signed link; the participant's choices occur in Tracker. `refreshResponseRsvpStatus()` refreshes those fields outside the sidebar. **RSVP Refreshed At** records the last successful reconciliation; **Last Sync** may also describe other operations and is not an RSVP-freshness signal. The **Cancellation Link** column remains for previously issued links. Do not treat a Sheet status as live without a recent successful refresh. See [`docs/RSVP_EMAIL_RUNBOOK.md`](../../docs/RSVP_EMAIL_RUNBOOK.md) before exporting or sending.
