## 2024-10-24 - Missing Authorization in `users.search`
**Vulnerability:** The `users.search` tRPC endpoint was only protected by authentication (`protectedProcedure`) without an explicit role check. This allowed any authenticated user to retrieve details (names, emails) of other users.
**Learning:** In this tRPC setup, `protectedProcedure` only guarantees authentication. It does not enforce role-based access control (authorization) out of the box unless explicitly checked within the procedure.
**Prevention:** Always verify if a `protectedProcedure` requires specific roles (like `ADMIN` or `ORGANIZER`) and use the `hasRoles` utility combined with `ctx.prisma.user.findUnique` to enforce these constraints. Additionally, ensure correct error propagation using `TRPCError`.

## 2024-10-24 - Missing Authorization in `teams.create` and Prisma Client Connection Leak
**Vulnerability:** The `teams.create` tRPC endpoint was exposed as a `publicProcedure`, allowing any user to join arbitrary teams on behalf of any `hackerId` due to missing authorization checks (Insecure Direct Object Reference / IDOR). Additionally, `PrismaClient` was being instantiated directly inside the router instead of utilizing the shared pool via `ctx.prisma`.
**Learning:** `publicProcedure` offers no authentication out of the box, and directly parsing `hackerId` without validating it against the session's `user.id` introduces severe IDOR vulnerabilities. Furthermore, local instantiations of `PrismaClient` in serverless/tRPC routers can lead to connection exhaustion.
**Prevention:** Always use `protectedProcedure` for endpoints requiring user validation, and explicitly verify that the provided input (e.g. `hackerId`) belongs to the authenticated `ctx.session.user.id`. Avoid `new PrismaClient()` in routers; always inject and use `ctx.prisma`.
